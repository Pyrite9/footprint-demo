# 시연 범위와 업무 규칙

출처: 업무 기능도 및 업무 기술서 v1.3(2026.10.22), 프로젝트 개요서 v4.4(2026.10.01), 팀 조장 2단계 로드맵(2026.10.15).
서비스 원칙: **판단은 사람, 시스템은 근거만.** 점수를 계산하지 않고 기록을 있는 그대로 보여 준다.

## 1. 시연 흐름 (12.11 학기 발표)

교수 로그인 → 과제 생성(조장 지정) → 조장이 초대 링크 발급 → 학생이 링크로 합류 → 조장이 역할 배정 → 조원이 산출물 업로드 → 조원·교수가 산출물 열람·다운로드 → 조원이 동료평가 제출

## 2. 만드는 순서

| 단계 | 기간 | 내용 | 밀리면 뒤로 보내는 것 |
|---|---|---|---|
| 0. 골격 | 바로 | 로그인 API, 내 정보 API(역할 포함), JWT 발급·검증, `SecurityFilterChain`, 401·403·409 오류 응답, CORS, `StorageService`, 시작 데이터, React Router·로그인 화면·로그인 안 하면 로그인 화면으로, `client.js`, 가짜 API | 로그아웃 버튼, 다운로드 예시 |
| 1. 과제·조·역할 | 10.26 ~ 11.01 | 과제 생성·목록·상세, 조 추가와 조장 지정, 초대 링크로 합류, 조원 목록과 역할 배정 | 화면 디자인 → 초대 링크 합류(시작 데이터로 대체) |
| 2. 산출물·한 번에 실행 | 11.02 ~ 11.08 | 산출물 업로드·순번·목록·다운로드, `docker compose up` 한 번으로 백엔드·화면·PostgreSQL·MinIO와 시작 데이터 실행, Postman 모음 | 화면의 nginx 이미지(개발 서버로 시연) → 다운로드 |
| 3. 동료평가 | 11.09 ~ 11.14 | 동료평가 입력·제출, 새로 clone 한 폴더에서 처음부터 끝까지 실행 | 없음. 11.14(토)는 미룰 수 없음 |

## 3. 1단계 기능 (8개)

| 기능 ID | 기능 | 1단계 단위 업무 | 2단계로 미룬 단위 업무 |
|---|---|---|---|
| M-1 | 회원가입 | M-1-1 회원 등록 | |
| M-2 | 로그인·로그아웃 | M-2-1 로그인·로그아웃 | |
| A-1 | 과제 생성 | A-1-1 과제 정보 입력, A-1-2 조장 지정 | |

| T-1 | 조원 초대 | T-1-1 초대 링크 발급, T-1-2 링크로 합류 | |

## 4. 업무 규칙

### 공통
- 기록 시각(업로드, 역할 지정, 평가 제출)은 서버가 저장한다. 사용자가 보낸 시각은 받지 않고 고칠 수 없다.
- **접근 범위는 1단계부터 적용한다.** 조의 기록을 다루는 요청마다 "그 조의 조원인가, 또는 그 과제를 만든 교수인가"를 서버가 확인한다. 다른 조의 기록은 주소를 직접 입력해도 403이다.
- 권한 검사는 Service 안에서 보이는 메서드 호출로 한다(예: `teamAccessChecker.checkMember(teamId, memberId)` 같은 한 곳의 메서드). `@PreAuthorize`·AOP는 12.12 이후 검토.
- 과제 단계(기록 단계·평가 단계) 구분은 2단계다. 1단계에서는 조원 합류를 마친 뒤 동료평가를 입력하는 것으로 운영한다.
- 시스템은 점수, 순위, 진척률을 계산하지 않는다. 평가 화면 위쪽에 아래 문구를 고정한다.
  - "업로드 횟수는 기여도가 아닙니다"
  - "점수는 시스템이 계산하지 않습니다"
- 산출물 파일 본문은 MinIO에, 데이터베이스에는 파일 위치, 이름, 크기만 저장한다.

### 회원 (M)
- 회원 유형은 교수, 학생 두 가지. 내 정보 응답에 회원 유형을 넣는다.
- 로그인하지 않은 사용자는 로그인 화면만 본다. 로그인 후에는 요청마다 JWT로 회원과 회원 유형을 확인한다.

### 과제 (A)
- 교수만 과제를 만든다. 입력은 과제명, 기간(시작일·종료일), 조 개수, 조마다 조장 한 명(가입한 학생을 이메일로 지정).
- 과제, 조, 조장을 **한 번에** 저장한다. 등록한 과제는 고치거나 지울 수 없다(수정·삭제 API 없음).
- 조장은 그 조의 첫 번째 조원으로 함께 등록된다. 한 학생을 같은 과제의 두 조에 조장으로 지정할 수 없다.
- 조회: 교수는 자기가 만든 과제와 그 조 전부, 조장·조원은 자기가 참여한 과제와 자기 조만.

### 조 운영 (T)
- 초대 링크는 조장만 발급한다. 링크에는 조의 초대 코드가 들어가고, 다시 발급하기 전까지 유효하다(재발급하면 이전 코드는 무효).
- 한 학생은 같은 과제에서 한 조에만 참여한다. 없는 초대 코드는 404 `NOT_FOUND`.
- 역할명은 조장이 정한다. 조장을 포함해 조원마다 역할 하나. 같은 역할을 여러 조원이 맡을 수 있다.
- 합류한 조원을 내보내는 기능은 없다.

### 산출물 (R-1)
- 역할이 배정된 조원만 올린다. 고친 파일도 덮어쓰지 않고 새로 올린다.
- 업로드할 때의 역할명을 산출물에 **복사해서** 저장한다. 나중에 역할이 바뀌어도 순번이 끊기지 않게 하기 위해서다.
- 화면은 같은 역할의 산출물에 올린 조원과 관계없이 업로드 순서대로 순번을 붙이고, 최신을 맨 위에 둔다.
- 조원과 그 과제의 교수가 열람·다운로드한다. 조회 수, 다운로드 수는 집계하지 않는다.
- 업로드는 서버를 거치는 방식. 크기 제한 20MB(`spring.servlet.multipart.max-file-size`, `max-request-size`). 파일이 빠졌거나 너무 크면 400 `INVALID_INPUT`.
- 다운로드는 `ResponseEntity<Resource>`. 한글 파일 이름이 깨지지 않게 `Content-Disposition`을 RFC 5987 형식으로.
- 서버가 시작할 때 MinIO 버킷이 없으면 만든다.

### 동료평가 (E-2)
- 같은 조 조원 중 자신을 뺀 **전원**에 대해 6개 항목 점수(1~5)를 모두 입력해야 제출된다. 대상 조원 전원의 평가를 한 번에 저장한다.
- 제출 전에 대상 조원 전원의 입력 내용을 한 화면에 보여 준다.
- 제출한 평가는 고칠 수 없다. 같은 평가자가 같은 대상을 두 번 평가하면 409 `DUPLICATE`(데이터베이스 unique 제약도 둔다).
- 조원별 서술 의견은 선택. 평가와 의견은 과제를 만든 교수만 열람한다(교수 열람 화면은 2단계라 1단계는 저장까지).
- 조원끼리는 서로의 평가를 볼 수 없다.

## 5. 데이터 (12.11에 필요한 엔티티 6개)

회원, 과제, 조, 조 참여, 산출물, 평가. 기여 항목과 완료확인은 만들지 않는다.

- 산출물과 평가는 회원이 아니라 **조 참여**를 참조한다. 같은 회원이라도 조마다 역할이 다르고, 이 관계가 조 단위 권한 검사의 기준이다.
- 평가는 6개 항목 점수를 열로 저장한다(`s1` ~ `s6` 또는 항목 이름 열). 평가자·대상 조합에 unique 제약.
- 조에는 초대 코드 열을 둔다.
- 산출물에는 업로드 당시 역할명 열을 둔다.
- 영문 클래스·테이블 이름과 세부 필드는 ERD 확정본(`../footprint-study/docs/`)을 따른다. 없으면 제안하고 묻는다.

## 6. 시작 데이터

교수 1명, 학생 10명, 과제 1개, 조 2개(각각 초대 코드), 조원과 역할명, 산출물 2건(파일 본문도 MinIO에 넣어 다운로드를 시험할 수 있게).
시작 계정의 아이디·비밀번호 표는 `backend/README.md`에 둔다. 비밀번호는 BCrypt로 저장한다.

## 7. 동료평가 항목과 점수 기준

신태섭(2018) 조별 과제 동료평가 행동기준평정척도. `frontend/src/constants/`에 이 문장 그대로 둔다. 2점과 4점은 인접한 두 기준의 중간이다.

| 항목 | 5점 | 3점 | 1점 |
|---|---|---|---|
| 목표 공유·협업 | 다른 조원과 같은 목표를 공유하며 협업을 잘 이루어냄 | 목표는 공유했지만 협업이 잘 이루어지지 않음 | 협업 없이 혼자서 과제를 진행함 |
| 역할 수행 | 맡은 역할을 책임감 있게 수행해 과제에 큰 도움이 됨 | 맡은 역할에 최소한의 노력만 들여 과제에 별로 도움이 되지 않음 | 맡은 역할을 하지 않아 과제에 피해를 줌(예: 연락 두절) |
| 격려·도움 | 다른 조원을 격려하고 돕기 위해 적극적으로 노력함 | 격려하거나 돕지는 않았지만 피해를 주지는 않음 | 돕지 않고 조원의 사기를 떨어뜨려 피해를 줌 |
| 온라인 소통 | 카카오톡 등 온라인에서 적극적으로 소통함 | 온라인에서 소극적으로 소통함 | 온라인 소통에 불참하거나 불성실함 |
| 대면 소통 | 대면 회의에서 적극적으로 소통함 | 대면 회의에서 소극적으로 소통함 | 대면 회의에 불참하거나 불성실함 |
| 진행 점검·보충 | 진행 과정에 계속 관심을 두고 부족한 부분을 보충하려 노력함 | 관심은 있었지만 부족한 부분을 보충하려 하지 않음 | 진행에 관심이 없고 발전시키려는 노력을 하지 않음 |

## 8. 만들지 않는 것 (12.12 이후)

기여 항목, 완료확인, 근거 패널, 교수 열람(조별 기록·평가 결과), 진척 시각화, 과제 단계 전환, 역할 변경, 산출물 삭제, 평가 임시 저장, 조장 교체, 메일 발송, LLM 기능.
흐름에 꼭 필요해 보여도 만들지 말고 먼저 묻는다.

## 9. 미정 — 걸리면 멈추고 묻는다

`decisions.md`에 "확정"으로 적힌 항목은 여기서 지운 것으로 본다.

1. **12.11 로그인 방식**: 학교 구글 계정(g.yju.ac.kr) 로그인을 넣을지, 시작 계정의 아이디·비밀번호로 시연할지. 기술서 v1.3은 구글 로그인(비밀번호를 받지 않음)이다. 어느 쪽이든 개발 중에는 시작 계정으로 로그인한다. 회원 엔티티 필드가 달라진다. → **2026.10.26 관리자 결정: 구글 로그인(g.yju.ac.kr). 교수는 설정값의 교수 이메일 목록으로 판별. 이메일·비밀번호 로그인은 개발·백업용으로 남긴다.**
2. **ERD 세부**: 조장을 조의 열로 둘지 조 참여의 행으로 둘지, 과제 필드(`description`, `status`, `professor_id`), 엔티티 영문 이름.
3. **로그인한 회원을 Controller에서 받는 방법**: 어노테이션과 받는 타입(회원 번호인지 회원 엔티티인지). 하나로 고정한다.
4. **token 저장 위치**(프론트엔드)와 그 이유.
5. **같은 회원이 같은 조에 다시 합류할 때** 처리(그대로 성공인지 409인지).
6. 없는 주소와 500 응답 형식, 400 응답에 틀린 필드를 담을지.
7. JWT 라이브러리와 S3 클라이언트 라이브러리 선택.
8. PBL 결과물 제출 형태(로컬 실행 묶음인지, 접속 가능한 주소인지). 답이 없으면 2단계는 둘 다 가능하게 만든다.
